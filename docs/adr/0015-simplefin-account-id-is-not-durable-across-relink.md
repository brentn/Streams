# SimpleFIN account id is not durable across a bank-side relink

Confirmed via live network inspection (Safari Web Inspector against the actual `/accounts` HTTP response, compared to the app's IndexedDB) that SimpleFIN can mint a brand-new `id` for an account across a bank-side relink at the Bridge, even though the connection's Access URL/credentials stay valid and the response comes back completely clean (HTTP 200, empty `errlist`/`errors`). Confirmed concretely: a Coast Capital account's server-reported id was `ACT-7f56a062-a8ee-4cb3-88c4-0901c311dba0`, while the app's stored record was `ACT-9ca4a5ce-5c89-4f7d-89f4-8711ea66eec4` — different ids, same real bank account.

`reconcileSyncedAccounts` (`resync-known-accounts.ts`) matches incoming SimpleFIN accounts against stored ones purely by `id`. An id mismatch means the fresh, clean data lands in its `newAccounts` bucket — which the regular resync path discards entirely, never looking at it. Result: a stale, still-Needs-Reauthentication stored account is never updated no matter how many times the user resyncs, even though the connection is completely healthy — #101's auto-retry-on-tab-return fix faithfully keeps retrying a resync that never actually changes anything for that account.

We're recovering these accounts by matching on `name` **and** `institutionName` equality against stored Accounts still marked Needs Reauthentication, but only while a resync is specifically recovering from that state (`isRecoveringFromNeedsReauth`) — never during an ordinary daily/manual resync. An unambiguous single match re-keys the stored Account (`StorageRepository.reidAccount`: writes it under the new id, relinks every Transaction/Flow/Transfer that referenced the old id) and merges in the fresh sync data, preserving the same locally-owned fields (`name`, `institutionName`, `expectedSign`, `dryFloor`) `reconcileSyncedAccounts` already preserves. Zero or multiple matches falls through to today's existing "silently not persisted" treatment, unchanged.

## Considered Options

- **Match on `name` alone** — rejected: during recovery the candidate pool is the user's *entire* account list (ADR-0003's connection-wide fan-out to every Account, not a narrow subset), so a generic shared name ("Checking") across two different institutions risks a false-positive match that merges one account's transaction history onto the wrong Account — actively corrupting data, strictly worse than the bug being fixed. `institutionName` is available at the same point as `name` and costs nothing extra to also require.
- **Auto-adopt on every resync, not just recovery** — rejected: keeps the blast radius narrow. An id mismatch during an otherwise-healthy resync is a different, unexplained situation this ADR's evidence doesn't cover; recovery is the one case with a known, confirmed cause.
- **Surface unmatched accounts to the user for manual confirmation (a reconciliation picker UI)** — rejected for now: Streams is a single-user app: the user confirmed they're comfortable doing a rare manual fix (re-running the connect flow, or a one-time backup edit) on the occasions auto-matching doesn't apply (a genuine rename mismatch on an account's first relink after this ships), rather than the app carrying a whole picker UI built for an edge case.
- **Track a separate `simplefinName`/`simplefinInstitutionName` pair on every Account, refreshed every sync, immune to local renames** — considered as the fully general long-term fix, deferred: adds a data-model field and a write on every successful sync for a benefit that only matters if the *same* Account gets re-issued a new id *again* after having also been locally renamed since the last relink — a rare compound case. `name`/`institutionName` matching against the current stored values is sufficient for the common case and can be revisited if the compound case actually recurs.

## Consequences

- Accounts already orphaned before this fix ships (this app's own affected accounts among them) don't self-heal automatically if their local `name` has since diverged from what SimpleFIN currently calls them (i.e. the user renamed the account in Streams) — those need a one-time manual bridge: export a backup, align the `name` field back to SimpleFIN's current name, re-import, then resync, so the matching logic can find them. Accounts never renamed self-heal with no user action at all.
- A false-negative (an id-reissued account matching zero or multiple candidates) is silently inert, same as today's pre-fix behavior — no new UI, no error surfaced. The user has to notice and act (a subsequent relink, or the manual bridge above).
- If SimpleFIN reissues an id for an Account *again* after a local rename has already diverged its `name`/`institutionName` from SimpleFIN's own values, this fix's matching won't fire and the same manual bridge is needed again — accepted as the rare compound case the deferred `simplefinName` tracking option above would close.
