# Ignored Transaction is a separate store, filtered into specific consumers rather than the shared Transaction signal

Surfaced by issue #104: some synced Transactions the user never wants to assign to a Flow, and wants gone from the "Needs categorization" list — but not too easy to remove by accident. Grilled alongside #105 (Direct Categorization, ADR-0018), since both are per-transaction decisions reached from the same UI surfaces (`TransactionReview`, `TributaryPanel`'s assign-match picker).

**Decision**: model this as a new concept, Ignored — `{transactionId}` in its own store (`ignoredTransactions`, schema v18), keyed by Transaction id.

## Considered Options

- **A field on `Transaction`** — rejected for the same reason ADR-0018 rejected it for Direct Categorization: `upsertTransactions` does a full-record `put` keyed by id on every resync, sourced from freshly-fetched wire data that never reads the previously-stored record (`resync-known-accounts.ts:68`). Any such field would be silently dropped on the next sync.
- **Filter the shared `transactions()` signal itself, upstream of every consumer** — rejected. `account-stream.ts` loads one `transactions()` signal shared by the review list, the tributaries, *and* `balanceAtDate`/`balanceSeries`/`runningDryAlert`. Those last three reconstruct the Account's actual and projected balance from real bank-reported Transaction history (ADR-0001) — they must include every Transaction regardless of the user's categorization choices. A global filter would have silently corrupted historical balance reconstruction and the Running-Dry projection for the sake of a categorization-list feature. Instead, the exclusion is threaded into the specific consumers that are actually about categorization/totals — the same shape ADR-0014 already established by threading `skippedOccurrences` into `withOutstandingOccurrences`/`withOutstandingTributaries` rather than filtering `flows()` wholesale.
- **Scope Ignore to only unmatched Transactions** — considered, then explicitly widened: an already-matched Transaction (rule-derived or Direct Categorized) can also be Ignored. Ignored is orthogonal to `matchedTarget` rather than a replacement for "unmatched" — it doesn't delete or check Direct Categorization/rules, it only suppresses.
- **A dismiss action that mutates/removes the Transaction's existing match** — rejected, same reasoning as ADR-0014's rejected "dismiss that deletes/mutates the Flow or Transaction": conflates "this shouldn't count" with "this is wrong/miscategorized," a different concept with its own edit/reassign flow already.
- **Recoverable via an "Ignored" view with an un-ignore affordance, in this same pass** — deferred, not rejected outright. Mirrors ADR-0014's Skipped Occurrence precedent: ship storage + suppression first, add the undo affordance later "if warranted," rather than building UI for a need not yet demonstrated.

## Consequences

- `StorageRepository` schema bumps to v18, adding the `ignoredTransactions` store (keyPath `transactionId`) — purely additive, no existing-data rewrite, same as v17's `directCategorizations`.
- Five call sites gain an `ignoredTransactions: IgnoredTransaction[]` parameter (defaulted to `[]`, matching this codebase's existing optional-collection convention), each already the specific place categorization-facing totals/lists are built: `TransactionReview`'s `unmatched` computation, `TributaryPanel`'s matched-Transaction list, `buildUncategorizedTributaries` (`core/charting/tributaries.ts`), `actualFlowMagnitude` (`core/projection/projection-engine.ts`) — the choke point both `varianceAlert` and `budgetProgress` (and through it, `aggregateBudgetProgress`) already call through, so Variance Alerts, Persistent Overrun Alerts, and the Budgets list total inherit the exclusion with no separate change needed at any of those call sites — and `averageMonthlyIncome`, surfaced during implementation as a fifth site: it already sums unmatched Transactions as income (deliberately, per its own doc comment — "real income may never get tied to a Flow at all"), so an Ignored Transaction would otherwise silently keep skewing the Budgets list's average-income figure even after disappearing from the Needs-categorization list. Excluded from the sum, but Ignored still counts toward the history span the average divides by — Ignored says "this shouldn't count," not "this account has less history than it does."
- `balanceAtDate`, `balanceSeries`, and `runningDryAlert` are deliberately left untouched — they keep reading the full, unfiltered `transactions()`.
- `apply-assignment.ts`'s `Assignment` union (and `assign-flow-dialog.ts`'s structurally identical `AssignFlowDialogResult`) gains an `{ mode: 'ignore'; transactionId: string }` variant. `applyAssignment` upserts into `ignoredTransactions` and returns the given Transactions unchanged — Ignore never touches `matchedTarget`.
- Two UI entry points, not one: a dedicated "Ignore" row action with a two-step inline confirm (mirroring `flow-form.html`'s Delete) on `TransactionReview`'s unmatched rows; and an "Ignore" action inside `AssignFlowDialog` — alongside the existing `removeDirectCategorization()` button, same no-extra-confirm bar — since that dialog (opened via `TributaryPanel`'s category badge) is the only existing entry point onto an already-matched Transaction.
- No UI reads `ignoredTransactions` back out for display yet — no un-ignore affordance in this pass, same deferral ADR-0014 made for Skipped Occurrence.
