# Budgets list follows the scrub position; progress-bar coloring reads Tolerance as a symmetric band

#82 asked the Budgets list's progress bars to react to the stream's scrub position instead of always showing real wall-clock "now" — a product decision that this list should read like the rest of the scrubbable stream (the balance line, every tributary) rather than sitting beside it as unwindowed current state.

This supersedes the last bullet of ADR-0010's Consequences, which chose real wall-clock "now" specifically to keep Budget Period math independent of the scrub position, reasoning that "a Budget Period is a real-calendar concept, not a projection the user is scrubbing through." That reasoning no longer applies: `BudgetList` now takes `selectedDate` as an input (the same `AccountStream.selectedDate`, derived from `dayOffset` via `date-window.ts`'s `selectedDateFor`) and passes it through to `budgetProgress` in place of `new Date()`. `currentPeriod` resolves against whatever period `selectedDate` falls in, so scrubbing to a future month with no Transactions yet shows an empty bar rather than the real current month's progress. The rest of ADR-0010 — no tributary rendering for budget-kind Flows — stays intact; only this one bullet is superseded. The uncategorized-transactions list stays unwindowed per ADR-0007, unaffected by this change.

#82 also asked each row's coloring to reflect proximity to its own Tolerance rather than a flat under/over split, and for the name and percentage to render as text overlaid on a full-width bar rather than squeezed beside a track that shrinks with the name's length. Both are handled inside `BudgetList`/`budget-list.html`; the percentage text shows the true, uncapped `used / limit`, while the bar's fill width is capped at 100%. Rows are sorted alphabetically by name.

**Tolerance's symmetric reading, distinct from Variance Alert**: `projection-engine.ts`'s `budgetProgressStatus(used, limit, tolerance)` reads a budget-kind Flow's `Tolerance` as a band centered on `limit` — `limit − toleranceAmount` to `limit + toleranceAmount` — regardless of `direction`: `ok` below the band, `warn` inside it, `over` above it. With no Tolerance set, there's no `warn` band: `ok` through `limit`, `over` past it. This is a second, distinct reading of the same `Tolerance` field CONTEXT.md's glossary entry describes for Variance Alert, which is single-directional for a budget-kind Flow (only the direction that hurts) and compares a *completed* period's actual against expected, not the *in-progress* period's `used` against `limit`. Both `budgetProgressStatus` and `varianceAlert` share the `toleranceAmount` helper for converting a `Tolerance` to a dollar amount, applying it differently: `varianceAlert` breaches in one direction off `expected`, `budgetProgressStatus` bands symmetrically off `limit`.

## Consequences

- `BudgetList` requires a `selectedDate` input; `account-stream.html` passes `selectedDate()` alongside `flows`/`transactions`. Any other future consumer of `BudgetList` must supply it too.
- CONTEXT.md's Tolerance entry describes only the Variance Alert reading; it doesn't (and isn't updated to) describe the Budgets list's symmetric-band reading, which lives here and in `budgetProgressStatus`'s doc comment instead — a deliberate choice to keep the glossary entry about the shared field's single canonical meaning (how far actual may differ from expected) rather than enumerating every consumer's use of it.
- No new CSS tokens: the existing `--color-accent` (ok), `--color-warning` (warn), and `--color-critical` (over) tokens cover the three states.
